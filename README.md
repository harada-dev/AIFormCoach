# PRD:AIフォームコーチ(仮称「AI_FormCoach」)

**バージョン:** 1.3 / **改訂日:** 2026-08-30 / **ステータス:** レビュー待ち

> **v1.2からの主な変更(すべてPhase 0の実機実測・実装に基づく)**
> 1. **角度規約(屈曲角/内角/鉛直からのずれ)のバグを発見・修正。** 膝の基準値(PRD・文献とも屈曲角)を、実装は内角で計算しており約20°の系統的なずれが未検出のまま残っていた。`Convention`型で規約を明示し、計測側と基準値側の不一致を機械的に検出できるようにした。**角度定義バージョンを2→3に更新**(v2の膝の値は再測定が必要)。
> 2. **処方できる指標は膝屈曲1つに確定。** 足首の伸びは足部キーポイントの推定誤差(足長の変動係数16〜29%)が測りたい差(6°)より大きく、構造的に処方不可能と判断。体幹前傾は基準値「15〜20°」の一次出典が確認できず撤回(実際の一次値は平均5.8°の後傾)。両指標とも計測値の表示と一般的な指導ポイントの提示(判定はしない)に切り替えた。
> 3. **測定窓(中央値)方式を導入。** インパクト付近で小さく速く動く指標は1フレームでは同一動作でも13〜15°ずれたが、膝最深から150ms区間の中央値を取ると1〜2°に収まった。
> 4. **測定誤差以下の逸脱では処方しない閾値(5°)を追加。** PRD G6「再現ばらつき±5°以内」に対応。0.4°のずれで素振り20回を指示するような誤った処方を防ぐ。
> 5. **骨格推定の破綻を検出・補間する仕組み(PoseIntegrity)を追加。** 骨長の一貫性から破綻フレームを検出し補間することで、品質ゲート通過率が**50%→75%**に改善。原因(カメラ角度・光量・履物・動作速度)は特定できなかったが、原因を特定せずに実用的な対策を打てることを確認した(§4.7参照)。
> 6. **運動連鎖(近位→遠位の順序)を参考指標として追加。** 処方はしないが、屋外の実戦動作では連鎖の時間差が安定(SD 5.3ms)することを確認。
> 7. **診断画面への導線が未接続だったバグを修正。** 実装はしていたが、アプリのどこからも`DiagnosisView`を呼び出していなかった。撮影後の確認画面と動画取り込み結果の両方から到達できるようにした。
> 8. **撮影記録の保存ライブラリ(直近20本+お気に入り最大5件)を追加。** 出自(自分の記録/受け取った記録)を区別して保存し、将来の比較機能で他人の骨格が混入しないようにした。
>
> **v1.1→v1.2の変更(継承):** §4「Phase 0 検証結果」の新設 / 角度計算を3D必須に / 必要フレームレートを120fps級に修正 / 骨格データサイズの実測改訂

## 1. 概要(エレベーターピッチ)

スポーツを練習する子ども・アマチュアのための、AIパーソナルコーチアプリ。ユーザーが自分のプレー動画を撮ると、AIが端末内で骨格を推定して動作を数値化し、**憧れの選手の「凄さ」を言葉で参照しながら、スポーツ科学に基づく基準値とのギャップを診断**。「最重要2点+理由+今日のドリル1つ+合格ライン」まで処方する。気持ちが沈んでいるときは実データに基づく励ましで継続を支える。将来的には、ユーザーが投稿する5秒動画を**骨格アニメーション化した「みんなのお手本」ライブラリ**へ育てる。第一弾の対象競技はサッカー(シュート/キック動作)。

## 2. コンセプトの核:参照コーチング(三段構成)

プロ選手の動画は権利上、取り込み・解析できない。本アプリは発想を反転し、**個人の映像データではなく、技術の知識をコーチングの基準にする**。動作・フォーム自体は著作権の保護対象ではなく、技術の言語化は事実・アイデアの伝達であるため、権利処理が不要になる。

| 段 | 内容 | 例(インステップシュート) |
|---|---|---|
| ① 憧れの参照(言葉) | 一流のプレーの「凄さ」を技術用語と平易な言葉で解説。動画は取り込まず、知識として言語化 | 「トップ選手は軸足の踏み込みが深く、蹴り足の膝を素早くたたんでバネを作る」 |
| ② 基準値(エビデンス) | スポーツ科学文献・指導者監修に基づく動作別の理想レンジをアプリ内DB化 | バックスイング時の膝屈曲 90〜110°、体幹前傾 15〜20° |
| ③ 自分の数値(診断) | ユーザー動画の骨格解析値を基準値と突合し、ギャップと処方を提示 | 「今日は134°。目標110°。かかとをおしりに近づける素振り×20」 |

**注意(パブリシティ権):** アプリ内の解説・批評文脈で選手名に触れることと、選手名を機能・広告の目玉にすることは別物。**マーケティングおよび機能名では選手名を使用しない**(法務確認必須)。

## 3. お手本の二層構造(視覚レイヤー)

- **第1層:自前お手本ライブラリ(MVP)** — 契約コーチ・提携クラブによる権利クリーンな実演動画。レベル別(U-10/U-12/中高生/上級)、3アングル、120fps撮影。
- **第2層:骨格化UGC「みんなのお手本」(v1.5)** — ユーザー投稿の5秒動画を、**生映像ではなく骨格アニメーション(棒人間/アバター)として公開**。個人を識別できないため未成年の安全とプライバシーを守りつつ、動きの情報は完全に保持される。

## 4. Phase 0 検証結果

iPhone実機で「撮影 → 端末内骨格推定 → 角度算出 → 診断・処方 → ファイル共有」までを実装し、実際のキック動作を撮影した骨格データを解析して技術前提を検証した。**以下はすべて実測値であり、推定ではない。**

### 4.1 骨格エンジン:MediaPipe 33点で確定

| 検証項目 | 結果 |
|---|---|
| 足部キーポイント(かかと/つま先)の検出 | **全302フレームで消失なし。** visibility平均0.86〜0.97、最低0.76 |
| Apple Vision framework との比較 | Visionは19関節で**かかと・つま先が存在しない**。インステップキックの足首底屈が原理的に測定不能 |

**結論:** 第一弾がキック動作である以上、足部4点を持つMediaPipeが必須。Visionは代替にならない。

**副次的発見:** 蹴り足と軸足でつま先の最大速度に**3〜6倍の差**が出た(右4.21〜9.67 対 左0.74〜1.50)。**利き足をユーザーに質問する必要がなく、自動判定できる。**設定項目を1つ削減。

### 4.2 角度計算:3D座標(worldLandmarks)を必須とする

2D画像座標で測った角度は、**撮影角度によって系統的にずれる**ことが判明した。遠近による短縮(foreshortening)が原因で、キーポイント自体の誤りではない。

足の長さを下腿長で割った比(解剖学的にはほぼ一定であるべき指標)で検証した。

| 条件 | 蹴り足の足長/下腿長比 |
|---|---|
| 2D・撮影角度が異なる2本 | 0.53 / 1.04(**2倍の差**) |
| 2D・撮影角度を揃えた2本 | 0.82 / 0.91(1割の差) |
| 2D・軸足(参考) | 0.78 / 0.78(完全一致) |

3D座標に切り替えると、骨の長さが解剖学的に妥当な値で安定した。

| 3Dでの骨長 | 中央値 | 変動係数 |
|---|---|---|
| 下腿(右) | 0.450 m | **2%** |
| 大腿(右) | 0.343 m | **3%** |
| 肩幅 | 0.302 m | 6% |

左右の大腿長が独立推定で一致(0.390m / 0.390m)するケースも確認しており、3D推定が体の構造を正しく捉えている。

**結論:** 角度計算はすべて3D座標で行う。2D座標での計測値は基準値DBと比較してはならない。実装上、計測結果に座標系のタグを持たせて混在を防ぐ。**角度定義バージョンを1→2に更新**(v1で測った値は再測定が必要)。

### 4.2.1 角度の「規約」の取り違えで約20°の系統的ずれ(v1.2で発見・修正)

3D座標を導入した後も、別の系統誤差が残っていた。**膝の基準値(PRD・文献とも「屈曲角:0°=完全伸展、値が大きいほど深く曲がる」という規約)を、実装は「内角:180°=完全伸展」で計算しており、両者の関係(屈曲角 = 180° − 内角)を変換せずに突き合わせていた。** これにより実測値が基準値レンジより約20°高く出続け、気づかれないまま基準値との比較が壊れていた。

対策として、計測結果に規約(`Convention`:屈曲角/内角/鉛直からのずれ)を明示的に持たせ、基準値の規約と一致しない値は診断エンジンが機械的に比較を拒否するようにした。**角度定義バージョンを2→3に更新**(v2で測った膝の値は再測定が必要)。

規約を揃えた結果、PRD・文献・実測が一致した。

| 出典 | 蹴り足の膝屈曲角(バックスイング最深) |
|---|---|
| PRD v1.2 §2(例示値) | 90〜110° |
| 文献(Cordeiro 2015 / Greig 2018、二次引用) | 93.3〜111.8° |
| Phase 0 実測(屋外実戦5本) | 90〜113° |

室内の軽い蹴り(4本)は屈曲角75〜82°と、屋外の実戦動作より一貫して不足側に出ており、指標として動作の強度・質を反映していることも確認した。

### 4.3 必要フレームレート:30fpsでは計測不能

キック動作は極めて短時間で完了するため、30fpsでは角度の極値が記録されない。

| 撮影条件 | 実効fps | 膝角の1フレーム変化(最大) | 足首角(最大) |
|---|---|---|---|
| 4K/60fps指定 | 9.6(推論が追いつかず8割破棄) | — | — |
| 720p/30fps | 30.0 | **51〜64°** | 62° |
| スローモーション取り込み | 30(実質240fps相当) | 16° | 21° |
| **アプリ内高fps撮影** | **104.5** | **5°**(95%点1.8°) | 12° |

つま先の最大速度は**9.67 m/s(時速35km)**。30fpsではピーク区間に14フレームしか存在せず、インパクト前後の角度が完全に欠落する。

**結論:** ライブ推論の高速化では解決しない。**高フレームレートで録画し、事後に全フレーム解析する二段構成**とする。104fpsの実測で目標(20°以下)を大きく下回ったため、**120fps級を仕様値とする**(240fpsは露光時間1/240秒の制約があり、屋外・体育館での実用性に懸念があるため過剰と判断)。

### 4.4 撮影条件:角度の固定が機能要件

4.2の検証から、**撮影角度を揃えないと数値が再現しない**ことが確定した。角度が違うと同じ動作でも異なる値になり、基準値DBとの突合が意味を持たない。

F1の撮影ガイドに「蹴る方向に対して真横」の指定を追加する。これは推奨ではなく必須要件。

あわせて実測から確定した撮影仕様:

- **解像度は720pで十分。** MediaPipeは内部で256px程度に縮小するため、4Kにしても精度は向上せず発熱のみ増加(4K/60fpsでは推論が9.6fpsまで低下)
- **全身が画角に収まること。** つま先が画角外に出ると足部指標が欠落する
- **自動診断(向き):** 骨格の縦横比が1未満なら映像の向きが90度ずれている(実測0.47で検出)。実行時チェックとして実装済み
- **自動診断(真横撮影):** 足長÷下腿長の比(スケールに依存しない)で真横撮影を判定できる。実測で真横0.25〜0.26、正面0.19。正面撮影では足部キーポイントが遠近短縮で3割短く推定され、軽い素振りでも本気のキックに近い値が出て誤診断になるため、閾値0.22を下回る指標(真横が必須の指標)は判定を保留する

### 4.5 熱設計

4K/60fpsは実機で即座に問題化した。720p/30fpsへの変更で、実効フレームレートが9.6→30.0fpsに向上しながら発熱は減少した。捨てるフレームを生成するコストが推論そのものより大きかったため。

**結論:** 撮影解像度・フレームレートは熱制約から先に決める。屋外の炎天下での検証は未実施(Beta時の必須項目)。

### 4.6 実装上の確定事項

- 骨格ファイル形式 `.fsc`(圧縮JSON)を策定。LINE/AirDrop経由の共有・再生を実機で確認
- Appleの`.zlib`圧縮は**zlibヘッダのない生DEFLATE**を出力する。Android版・サーバー側で読む際は要注意
- MediaPipeの`MPImage`は向き指定を反映しない。動画解析時はピクセル自体の回転が必要
- **リソースは`AIFormCoach/`直下に置く。** ターゲットはXcodeのフォルダ同期(`PBXFileSystemSynchronizedRootGroup`, `path = AIFormCoach`)を使っており、`AIFormCoach/`配下は自動で同梱される。裏を返すと、それ以外の場所に置いた`.task`はビルドが通っても実行時に`modelNotFound`になる。逆に大きい検証用ファイルを誤って`AIFormCoach/`に置くと製品版に混入する
- モデルは`lite`/`full`/`heavy`の3つとも使用中(ライブ/動画解析の既定/高精度)。合計44.6MBあるが、バンドルサイズ削減の目的で削ってはいけない。減らすならオンデマンドリソース化を検討する

### 4.7 測定窓(区間の中央値)方式で時間解像度の指標を安定化

足首のように小さく速く動く部位は、インパクト付近の1フレームだけを見ると、つま先の速度が9ms間隔で0.79→3.10→1.72 m/sのように激しく振動し(座標の微分によるノイズ増幅)、同一動作でも1フレーム方式では**13〜15°**ずれた。

対策として、局面の起点(膝最深)を長い骨(下腿・大腿)から安定に検出し、そこから150ms区間に含まれる全フレームの**中央値**を採用する方式に変更。中央値を使うのは、区間内に1〜2枚の外れ値が混じっても平均のように結果が動かないため。

| 比較(同じ動作の2本) | 1フレーム方式 | 窓の中央値方式 |
|---|---|---|
| 素振り(横) | 13°の差 | **2°の差** |
| 本気のキック | 15°の差 | **1°の差** |

### 4.8 処方できる指標は膝屈曲1つに確定

3指標(膝屈曲・体幹前傾・足首の伸び)を実測で検証した結果、**処方(合否判定+ドリル提示)に使えるのは膝屈曲のみ**という結論に至った。

| 指標 | 再現性(SD) | 判別力 | 結論 |
|---|---|---|---|
| 膝屈曲 | 1〜3° | 155°→106°(強度に応じ単調に変化) | **処方可能** |
| 体幹前傾 | 3〜6° | 6°→15°で変化 | 基準値の一次出典が確認できず撤回。参考値のみ |
| 足首の伸び | 1〜2°(窓方式) | 意図的に伸ばした111° 対 伸ばさない105°で**差6°** | 測りたい差(6°)が推定誤差(足長の変動係数16〜29%→角度換算10°以上)より小さく、構造的に処方不可能 |

**体幹前傾について:** PRD記載の「15〜20°」は一次出典が確認できず撤回した。確認できた一次値(Alcock et al. 2012、エリート女子選手n=15)は平均**5.8°の後傾**であり、前傾15〜20°を支持しない。実測でも、上体を残す意識で蹴った1本はシュートモーションが長くなる傾向を示しており、前傾・後傾いずれが良いという基準を設けず計測値のみ表示する。

**足首の伸びについて:** 指導上は重要(足首が緩むと当たり負けして力が逃げる)と分かっているが、現状の計測系では判別できないと結論。処方はしないが、「インステップで蹴るときは足首を固定するのが共通のポイント」という、計測値によらない一般的な指導ポイント(coachingNote)は別途表示する。**測れていない数値を根拠に「あなたはできていない」と言わない**ことと、**測定と無関係に正しい一般論を伝える**ことを、実装上も型で区別している。

復活の道筋は複数アングルからの3D推定(§9.3将来バックログ)。

### 4.9 測定誤差以下の逸脱では処方しない

膝屈曲は再現性SD 3.1〜7.6°だが、逸脱0.4°(基準値からわずかに外れただけ)でも処方が発動してしまう実装上の問題が見つかった。「+0°ずれています」と言って素振り20回を指示するのは不自然であり、**測定誤差の範囲内では「範囲内」として扱う**閾値(5°、PRD G6の±5°に対応)を導入した。導入後、実測の逸脱0.4°のクリップは処方なし、逸脱8〜15°のクリップは処方あり、という妥当な分かれ方になることを確認した。

### 4.10 骨格推定の破綻を検出・補間し、原因を特定せずに実用対策を打つ

品質ゲート(計測窓内の信頼できるフレーム比率)を導入したところ、手元のデータの半分(8/16本)が不通過だった。**カメラ角度・光量・履物・動作の速さのいずれも、不通過を説明できなかった(相関0.25前後)。** 原因を特定できないまま、次の一手として「同一人物の骨の長さはクリップ内で変わらない」という不変量を使う対策を実装した。

**原理:** クリップ全体の骨長(股-膝、膝-足首、左右)の中央値から15%を超えて外れるフレームは、関節の対応付けを誤っている(左右の脚の取り違えなど)と判断できる。原因(なぜ取り違えたか)を特定しなくても、「このフレームは信用できない」と機械的に言えるのが利点。破綻フレームは前後の健全フレームから座標を補間する(visibilityは書き換えず、そのフレームが不確かだった事実は残す)。

**効果:** 品質ゲート通過率が **50%(8/16)→75%(12/16)** に改善。通過していたクリップの値は変化しない(93°→93°、110°→110°)ため、**壊れていないものを壊さない**という条件も満たしている。

| クリップ | 窓内健全率 | 補間前 | 補間後 |
|---|---|---|---|
| 大人 07-31 | 15% | 117°/スパイク7 | 117°/**1** |
| 大人 07-33 | 31% | 122°/4 | 122°/**1** |
| 大人 11-46 | 50% | 103°/4 | 96°/**0** |
| 大人 11-47 | 23% | 120°/6 | 112°/**1** |
| 大人 07-34 | 37% | 112°/9 | 110°/3(不可) |
| 11歳 07-27 | **0%** | 137°/7 | 91°/2(不可) |

窓内健全率が0%のクリップ(補間の元データが窓内に一枚もない)は原理的に復元できず、撮り直しを案内する。この案内文も**原因を断定しない**書き方にしている(前述の通り原因を特定できていないため)。「真横から撮ってください」のような断定的な指示ではなく、試せる選択肢(離れて全身を映す/カメラ位置を変える/力を抑える 等)を並べる形とした。

### 4.11 運動連鎖(近位→遠位)は参考指標として有効

キックを股関節→膝→足首の運動連鎖として捉え、大腿・下腿の角速度ピークの時間差(近位→遠位の順で加速するのが理想)を計測した。**処方には使わないが、動作の質を反映する参考指標として有効**と判断した。

- 屋外の実戦動作では連鎖の時間差が安定(26/34/36ms、SD 5.3)
- 室内の軽い蹴りでは崩れる(34/51/76/136ms、SD 44.6) — 運動連鎖が形成されていないことを示唆
- タイミング効率(ボール接触時/ピーク時の角速度比)は技量を分離しないが(大人94〜97% 対 13歳69〜94%で重なる)、推定破綻の検出には有効(異常クリップで20%、他は94〜97%)

### 4.12 診断画面への導線漏れと、保存ライブラリの追加

実装は完了していたが、**アプリのどこからも`DiagnosisView`を呼び出しておらず、実機で診断画面に到達できない状態**が長く残っていた(コードレビューで発覚)。撮影後の確認画面と、動画取り込み結果の画面の両方に、蹴り足選択+「診断を見る」導線を追加して解消した。

あわせて、`.fsc`が一時ディレクトリ(iOSがいつ削除しても仕様通りの領域)にしか残らず見返せない問題を解消するため、撮影記録の保存ライブラリを追加した。直近20本を自動保存、お気に入りは最大5件(一言メモ付き、直近の枠から独立)。**出自(自分で撮った/受け取った)を明示的に記録する**のは、将来「前回比+5°」のような比較機能を作ったときに、他人の骨格が比較対象に混ざらないようにするため。

## 5. UGC設計:審査型ライブラリ(開放型SNSにしない)

低品質・誤ったフォームの拡散を防ぐため、フィード型SNSではなく**キュレーションされた集合知**(Wikipedia型)として設計する。

**投稿フロー:** ①5秒動画を投稿(端末内で骨格化済み)→ ②AI自動審査(骨格信頼度/撮影条件/基準値適合)→ ③合格分のみ骨格アニメとして「みんなのお手本」へ、レベル帯に自動分類 → ④認定コーチ(バッジ制度)が任意でレビュー・解説付与。

**運用ルール:** 公開は骨格アニメ+匿名ハンドルのみ(生動画は本人・保護者限定)/リアクションは肯定系のみ(👏🔥「まねした」)、自由コメントなし/DM機能を作らない/週次チャレンジでテーマを限定/通報導線と24h対応SLA、未成年関連は最優先キュー。

**v1.2で追加:** 解析用の高フレームレート・3D骨格(5秒で約240KB)をそのまま公開すると容量が想定の6倍になる。**公開用は30fps・2Dにダウンサンプリングした軽量版(約15KB)を別途生成する**(§9.3参照)。閲覧に高フレームレートと3Dは不要。

## 10. インフラ・コスト戦略

### 10.1 設計原則

1. **端末内完結の最大化** — 骨格推定・平滑化・フェーズ分割・角度計算・基準値突合・ギャップ判定まで、解析パイプライン全体を端末内で実行する。サーバーが必要なのは「コンテンツ配信」「処方の言語化(LLM)」「UGC共有」の3つだけ。**Phase 0で実機動作を確認済み。**
2. **自前サーバーを建てない** — バックエンドはBaaSを採用し、認証・DB・ストレージ・軽量処理をマネージドで賄う。
3. **骨格データの軽さを武器にする** — ただし**v1.1の想定(5秒≈40KB)は2Dのみの前提であり、実測で修正が必要**(下表)。

### 10.2 骨格データサイズ(実測に基づく改訂)

| 用途 | 内容 | 5秒あたり(圧縮後) |
|---|---|---|
| v1.1想定 | 2Dのみ・30fps | 40KB |
| **解析用(実測)** | **3D込み・30fps** | **約75KB** |
| **解析用(実測)** | **3D込み・120fps級** | **約240KB** |
| **公開用(v1.5)** | **2D・30fpsへダウンサンプル** | **約15KB** |

**UGCライブラリには公開用の軽量版のみを保存する。**1万投稿で約150MBとなり、BaaS無料枠に収まる。高精度な解析用データは端末内に留める。

### 10.3 段階的インフラ計画

| フェーズ | インフラ | 月額目安 | 内容 |

インフラ費の主役はサーバーやストレージではなく**LLM API呼び出し(処方文の生成)**である。

## 11. システム構成(改訂)

```
[モバイルアプリ(端末内で完結する処理)]
  ├─ 【撮影中】720p/30fps・軽量モデルでライブガイド
  │    └─ 全身の画角判定 → 静止検出 → 自動収録開始
  ├─ 【録画】120fps級で動画を保存(AVAssetWriter)
  ├─ 【事後解析】全フレームを高精度モデルで処理(runningMode=video)
  │    └─ 33点+3D座標 → 平滑化 → フェーズ分割 → 3Dで角度算出
  ├─ 基準値DB(同梱・差分更新)と突合 → 診断ビュー/成長記録
  ├─ .fsc 書き出し・読み込み(F11)/ 公開用の軽量版生成(v1.5)
  └─ 処方キャッシュ(同一ギャップパターンはLLMを呼ばず再利用)
        │ 必要時のみ・軽量データのみ
        ▼
[BaaS(Supabase/Firebase — 自前サーバーなし)]
  ├─ 認証(匿名→保護者アカウント昇格)
  ├─ 公開用骨格データDB+審査キュー(v1.5)
  ├─ 参照コーチングDB・基準値の配信(出典・監修者・版管理)
  └─ お手本動画のCDN配信
        │
        ▼
[LLM API]
  └─ 処方生成:計測値/基準値ギャップの構造化JSON → 三段構成の処方文
     (セーフティフィルタ:医療助言・過負荷・ネガティブ表現の検出)
```

**ライブガイドと解析を分離したことがv1.2の最大の構造変更。**リアルタイム推論では時間解像度が足りず、逆に解析パスはリアルタイム制約がないため高精度モデルで全フレームを処理できる。

要点:LLMには動画を渡さず**構造化データのみ**。生動画・生骨格の既定保存先は端末。

## 14. リスクと対策

| リスク | 影響 | 対策 | 状態 |
|---|---|---|---|
| 基準値の妥当性不足 | 誤った指導 | 文献出典+複数コーチ監修+年齢帯別レンジ、定期レビュー。「目安」として提示。**体幹前傾は一次出典を確認できず基準値を撤回済み(§4.8)** | 一部対策 |
| **計測値の撮影角度依存** | **基準値と比較不能** | **3D座標での角度計算(実測で有効性を確認)+F1での角度指定+真横撮影の自動判定(足長/下腿長比、§4.4)** | **対策済み** |

## 16. オープンな論点

**実測で解決した論点(v1.2〜v1.3)**
- ~~骨格エンジンの選定~~ → MediaPipe 33点で確定(足部キーポイントが必須のため)
- ~~角度計算の方式~~ → 3D座標必須で確定(2Dは撮影角度依存で再現しない)
- ~~角度の規約~~ → 屈曲角/内角/鉛直からのずれを型で区別し、PRD・文献・実測を整合(§4.2.1)
- ~~実用フレームレートの決定~~ → 120fps級を仕様値として確定。測定窓の中央値方式と組み合わせて時間解像度5°/frame相当を達成(§4.7)
- ~~足首の伸びは処方に使えるか~~ → 構造的に不可能と確定(§4.8)。参考値+一般的な指導ポイントに切り替え
- ~~体幹前傾の基準値15〜20°は妥当か~~ → 一次出典を確認できず撤回(§4.8)
- ~~骨格推定の断続的な破綻は放置するしかないか~~ → 骨長一貫性による補間で通過率50%→75%(§4.10)。ただし根本原因は未特定のまま

**未解決の論点**
1. 基準値DBの監修体制と年齢・体格帯別レンジの粒度 **(Alphaの最優先課題。膝屈曲1指標にまず絞る)**
2. BaaSの最終選定(Supabase vs Firebase — Alphaのスパイクで決定)
3. フリーミアムの線引き(無料:解析+基本処方/有料:詳細処方・履歴無制限・チャレンジ特典)
4. 認定コーチバッジの審査基準と有料メンター化の是非
5. 骨格アバターの表現(棒人間かキャラクター性のあるアバターか — 早期プロトタイプで検証)
6. UGC投稿規約(骨格データの利用許諾、退会時の扱い)
7. **撮影角度の担保方法** — 足長/下腿長比による自動判定は実装済み(§4.4)。閾値0.22の妥当性を、より多様な体格・年齢のデータで検証する必要が残る
8. **骨格推定が断続的に破綻する根本原因** — カメラ角度・光量・履物・動作速度のいずれとも相関しなかった(相関0.25前後)。補間による実用対策は打てたが、原因不明のままである点はBetaでも継続調査したい
9. **(新規) 運動連鎖(§4.11)の基準値** — 参考指標として有効性は確認できたが、処方に使える段階の基準値はまだない。監修と合わせて検討
