## 1. 概要(エレベーターピッチ)

スポーツを練習する子ども・アマチュアのための、AIパーソナルコーチアプリ。ユーザーが自分のプレー動画を撮ると、AIが端末内で骨格を推定して動作を数値化し、**憧れの選手の「凄さ」を言葉で参照しながら、スポーツ科学に基づく基準値とのギャップを診断**。「今日直すべき点+理由+今日のドリル1つ+合格ライン」まで処方する。気持ちが沈んでいるときは実データに基づく励ましで継続を支える。将来的には、ユーザーが投稿する5秒動画を**骨格アニメーション化した「みんなのお手本」ライブラリ**へ育てる。第一弾の対象競技はサッカー(シュート/キック動作)。

## 2. コンセプトの核:参照コーチング(三段構成)

プロ選手の動画は権利上、取り込み・解析できない。本アプリは発想を反転し、**個人の映像データではなく、技術の知識をコーチングの基準にする**。動作・フォーム自体は著作権の保護対象ではなく、技術の言語化は事実・アイデアの伝達であるため、権利処理が不要になる。

| 段 | 内容 | 例(インステップシュート) |
|---|---|---|
| ① 憧れの参照(言葉) | 一流のプレーの「凄さ」を技術用語と平易な言葉で解説。動画は取り込まず、知識として言語化 | 「トップ選手は蹴り足の膝を素早くたたんでバネを作る」 |
| ② 基準値(エビデンス) | スポーツ科学文献・指導者監修に基づく動作別の理想レンジをアプリ内DB化 | バックスイング時の膝屈曲 **90〜110°(屈曲角。0°=完全伸展)** |
| ③ 自分の数値(診断) | ユーザー動画の骨格解析値を基準値と突合し、ギャップと処方を提示 | 「今日は78°。目標90°。かかとをおしりに近づける素振り×20」 |

**角度の規約について:** 本文書の膝の角度はすべて**屈曲角**(0° = 完全に伸びた状態、値が大きいほど深く曲がっている)で表記する。キーポイントから直接得られるのは内角(180° = 完全伸展)で、`屈曲角 = 180° − 内角` の関係にある。この取り違えが約20°の系統誤差を生んでいた経緯は §4.2.1 を参照。

**v1.3で撤回:** かつてここに記載していた「体幹前傾 15〜20°」は一次出典が確認できず撤回した(§4.8)。現在、処方に使える基準値をもつ指標は膝屈曲のみ。

**注意(パブリシティ権):** アプリ内の解説・批評文脈で選手名に触れることと、選手名を機能・広告の目玉にすることは別物。**マーケティングおよび機能名では選手名を使用しない**(法務確認必須)。

## 3. お手本の二層構造(視覚レイヤー)

- **第1層:自前お手本ライブラリ(MVP)** — 契約コーチ・提携クラブによる権利クリーンな実演動画。レベル別(U-10/U-12/中高生/上級)、3アングル、120fps撮影。
- **第2層:骨格化UGC「みんなのお手本」(v1.5)** — ユーザー投稿の5秒動画を、**生映像ではなく骨格アニメーション(棒人間/アバター)として公開**。個人を識別できないため未成年の安全とプライバシーを守りつつ、動きの情報は完全に保持される。

## 4. Phase 0 検証結果

iPhone実機で「撮影 → 端末内骨格推定 → 角度算出 → 診断・処方 → 保存・共有」までを実装し、実際のキック動作を撮影した骨格データを解析して技術前提を検証した。**以下はすべて実測値であり、推定ではない。**

評価に用いたのは撮影条件を揃えた16本(大人9本・13歳6本・11歳1本、屋外昼/屋外ナイター/室内)。アプリの動作確認用に撮影した初期のデータは条件が揃っていないため評価から除外している。

### 4.1 骨格エンジン:MediaPipe 33点で確定

| 検証項目 | 結果 |
|---|---|
| 足部キーポイント(かかと/つま先)の検出 | 全302フレームで消失なし。visibility平均0.86〜0.97、最低0.76 |
| Apple Vision framework との比較 | Visionは19関節で**かかと・つま先が存在しない**。インステップキックの足首底屈が原理的に測定不能 |

**結論:** 第一弾がキック動作である以上、足部4点を持つMediaPipeが必須。Visionは代替にならない。

なお、足部キーポイントが「消失しない」ことと「精度が足りる」ことは別問題である。後者は満たされなかった(§4.8)。

#### 4.1.1 利き足の自動判定は不採用(v1.4で訂正)

初期の検証で、蹴り足と軸足のつま先の最大速度に3〜6倍の差が出たため「利き足をユーザーに質問せず自動判定できる」と判断していたが、**この結論は撤回する。**

その後の実測で、**軸足のつま先速度が 44 m/s(時速160km)という物理的にありえない値**を示すクリップが現れ、速度比較による判定が反転した。原因は足部キーポイントの推定不安定(§4.8)であり、判定の基礎そのものが信頼できない。

実装では蹴り足を明示指定する方式を採用している(撮影後の確認画面で左右を選択)。自動判定のコードは残しているが、既定では使用しない。

### 4.2 角度計算:3D座標(worldLandmarks)を必須とする

2D画像座標で測った角度は、**撮影角度によって系統的にずれる**。遠近による短縮(foreshortening)が原因で、キーポイント自体の誤りではない。

足の長さを下腿長で割った比(解剖学的にはほぼ一定であるべき指標)で検証した。

| 条件 | 蹴り足の足長/下腿長比 |
|---|---|
| 2D・撮影角度が異なる2本 | 0.53 / 1.04(**2倍の差**) |
| 2D・撮影角度を揃えた2本 | 0.82 / 0.91(1割の差) |
| 2D・軸足(参考) | 0.78 / 0.78(完全一致) |

3D座標に切り替えると、骨の長さが解剖学的に妥当な値で安定した。

| 3Dでの骨長 | 中央値 | 変動係数 |
|---|---|---|
| 下腿(右) | 0.41〜0.45 m | 5〜12% |
| 大腿(右) | 0.33〜0.39 m | 5〜11% |
| 足部(かかと-つま先) | 0.10〜0.12 m | **16〜29%** |

左右の大腿長が独立推定で一致(0.390m / 0.390m)するケースも確認しており、3D推定が体の構造を捉えている。**ただし足部だけは全群で16〜29%の変動があり、これが後の指標却下につながる(§4.8)。**

**結論:** 角度計算はすべて3D座標で行う。2D座標での計測値は基準値DBと比較してはならない。実装上、計測結果に座標系のタグ(`Space`)を持たせて混在を防ぐ。

#### 4.2.1 角度の「規約」の取り違えで約20°の系統誤差(v1.3で発見・修正)

3D座標を導入した後も、別の系統誤差が残っていた。

膝の基準値(PRD・文献とも「**屈曲角**:0°=完全伸展、値が大きいほど深く曲がる」規約)に対し、**実装は「内角:180°=完全伸展」で計算しており、両者を変換せずに突き合わせていた。**実測値が基準値レンジより約20°高く出続けたが、気づかれないまま比較が壊れていた。

対策として、計測結果に規約(`Convention`:屈曲角/内角/鉛直からのずれ)を明示的に持たせ、基準値の規約と一致しない値は診断エンジンが機械的に比較を拒否するようにした。角度定義バージョンを2→3に更新(v2で測った膝の値は再測定が必要)。

規約を揃えた結果、**PRD・文献・実測が一致した。**

| 出典 | 蹴り足の膝屈曲角(バックスイング最深) |
|---|---|
| PRD §2(例示値) | 90〜110° |
| 文献(Cordeiro 2015 / Greig 2018、**二次引用・原典未取得**) | 93.3〜111.8° |
| **Phase 0 実測(屋外実戦5本)** | **90〜113°** |

室内の軽い蹴り(4本)は屈曲角 **75〜82°** と一貫して不足側に出ており、指標が動作の強度・質を反映していることも確認した。

**教訓:** 数値が「なんとなく合わない」状態を放置すると、系統誤差が仕様の一部として固定される。規約は型で表現し、機械的に照合させるべきである。

### 4.3 必要フレームレート:30fpsでは計測不能

| 撮影条件 | 実効fps | 膝角の1フレーム変化(最大) |
|---|---|---|
| 4K/60fps指定 | 9.6(推論が追いつかず8割破棄) | — |
| 720p/30fps | 30.0 | **51〜64°** |
| スローモーション取り込み | 30(実質240fps相当) | 16° |
| アプリ内高fps撮影 | 104〜119 | **5〜8°** |

**結論:** ライブ推論の高速化では解決しない。**高フレームレートで録画し、事後に全フレーム解析する二段構成**とする。120fps級を仕様値とする(240fpsは露光時間1/240秒の制約があり、屋外・体育館での実用性に懸念があるため過剰と判断)。

### 4.4 撮影条件:角度の固定が機能要件

撮影角度を揃えないと数値が再現しない。F1の撮影ガイドに「蹴る方向に対して真横」の指定を追加する。これは推奨ではなく必須要件。

実測から確定した撮影仕様:

- **解像度は720pで十分。** MediaPipeは内部で256px程度に縮小するため、4Kにしても精度は向上せず発熱のみ増加
- **全身が画角に収まること。** つま先が画角外に出ると足部指標が欠落する
- **自動診断(向き):** 骨格の縦横比が1未満なら映像の向きが90度ずれている(実測0.47で検出)。実装済み
- **自動診断(真横撮影):** 足長÷下腿長の比(スケール非依存)で判定する。**実測レンジは 0.21〜0.33** で、群によっては 0.70 を超える値も出た。正面撮影では 0.19 まで下がり、足部が遠近短縮で3割短く推定されるため、軽い素振りでも本気のキックに近い値が出て誤診断になる。閾値0.22を下回る指標(真横が必須の指標)は判定を保留する

**閾値0.22の妥当性は未解決。** 体格・年齢・撮影距離によりレンジが広く、より多様なデータでの検証が必要(§16)。

### 4.5 熱設計

4K/60fpsは実機で即座に問題化した。720p/30fpsへの変更で、実効フレームレートが9.6→30.0fpsに向上しながら**発熱は減少した**。捨てるフレームを生成するコストが推論そのものより大きかったため。

**結論:** 撮影解像度・フレームレートは熱制約から先に決める。**屋外の炎天下での検証は未実施**(Beta時の必須項目)。

### 4.6 実装上の確定事項

- 骨格ファイル形式 `.fsc`(圧縮JSON)を策定。LINE/AirDrop経由の共有・再生を実機で確認
- Appleの`.zlib`圧縮は**zlibヘッダのない生DEFLATE**を出力する。Android版・サーバー側で読む際は要注意
- MediaPipeの`MPImage`は**向き指定を反映しない**。動画解析時はピクセル自体の回転が必要
- **リソースは `AIFormCoach/` 直下に置く。** ターゲットはXcodeのフォルダ同期(`PBXFileSystemSynchronizedRootGroup`)を使っており、この配下は自動で同梱される。それ以外の場所に置いた`.task`はビルドが通っても実行時に`modelNotFound`になる。逆に検証用の大きいファイルを誤って置くと製品版に混入する
- モデルは lite/full/heavy の3つとも使用中(ライブ/動画解析の既定/高精度)。合計44.6MB。バンドルサイズ削減の目的で削ってはいけない。減らすならオンデマンドリソース化を検討する
- **Xcode 26 の既定は全型が `@MainActor`。** バックグラウンド処理を書く型には明示的な対処が必要(プロジェクト設定で Default Actor Isolation を `nonisolated` にする、または型に `nonisolated` を付ける)

### 4.7 測定窓(区間の中央値)方式で時間解像度の指標を安定化

足首のように小さく速く動く部位は、インパクト付近の1フレームだけを見ると、つま先の速度が9ms間隔で 0.79 → 3.10 → 1.72 m/s のように激しく振動する(座標の微分によるノイズ増幅)。同一動作でも1フレーム方式では13〜15°ずれた。

対策として、局面の起点(膝最深)を**長い骨(下腿・大腿)から安定に検出**し、そこから150ms区間に含まれる全フレームの**中央値**を採用する方式に変更。中央値を使うのは、区間内に1〜2枚の外れ値が混じっても平均のように結果が動かないため。

| 比較(同じ動作の2本) | 1フレーム方式 | 窓の中央値方式 |
|---|---|---|
| 素振り(横) | 13°の差 | **2°の差** |
| 本気のキック | 15°の差 | **1°の差** |

**設計原則として一般化できる:** 局面の検出には推定が安定した長い骨を使い、精度の劣る部位の値は区間の中央値で読む。座標の微分(速度)は局面検出に使わない。

### 4.8 処方できる指標は膝屈曲1つに確定

3指標を実測で検証した結果、**処方(合否判定+ドリル提示)に使えるのは膝屈曲のみ**という結論に至った。

| 指標 | 再現性(SD) | 判別力 | 結論 |
|---|---|---|---|
| 膝屈曲(屈曲角) | 3.1〜7.6° | 室内 75〜82° 対 屋外実戦 90〜113° | **処方可能** |
| 体幹前傾 | 2.8〜14.7° | 自然体 +18〜23° 対 後傾意識 −5° | 基準値の一次出典が確認できず撤回。参考値のみ |
| 足首の伸び | 1.8〜7.8°(窓方式) | 意図的に伸ばした 111° 対 伸ばさない 105°(**差 6°**) | 測りたい差が推定誤差より小さく、**構造的に処方不可能** |

**足首の伸びについて:** 指導上は重要(足首が緩むと当たり負けして力が逃げる)と分かっているが、足長の変動係数が全4群で16〜29%あり、10cmの足に対して±2〜3cmの誤差、角度換算で10°以上になる。**測りたい差(6°)が誤差より小さい。**環境・被験者・履物を変えても改善せず、MediaPipeの足部キーポイント(2点)の構造的な限界と判断した。角度規約の換算では解決しない(誤差の床が下がらない)。

処方はしないが、「インステップで蹴るときは足首を固定するのが共通のポイント」という**計測値によらない一般的な指導ポイント(`coachingNote`)は別途表示する。**測れていない数値を根拠に「あなたはできていない」と言わないことと、測定と無関係に正しい一般論を伝えることを、実装上も型で区別している。

**体幹前傾について:** 「15〜20°」は一次出典が確認できず撤回。確認できた一次値(Alcock et al. 2012、エリート女子 n=15)は**平均5.8°の後傾**であり、前傾15〜20°を支持しない。加えて実測で、上体を残す意識で蹴った1本は**シュートモーションが長くなる**傾向を示した(実戦では不利益になりうる)。さらに膝の深さと強く連動しており(r = −0.85)、独立した指標でない可能性もある。前傾・後傾いずれが良いという基準を設けず計測値のみ表示する。

なお実装の誤りも1つ修正した。旧実装は `atan2(√(dx²+dz²), |dy|)` で**符号が失われており、前傾13°と後傾13°が同じ値**になっていた。文献値(後傾)と比較できない状態だったため、前方向を肩ライン・鼻から判定して符号付きに改めた。

復活の道筋は**複数アングルからの3D推定**(§9.3 将来バックログ)。

### 4.9 測定誤差以下の逸脱では処方しない

膝屈曲の再現性はSD 3.1〜7.6°だが、**逸脱0.4°でも処方が発動する**実装上の問題が見つかった。「+0°ずれています」と言って素振り20回を指示するのは不自然である。

測定誤差の範囲内では「範囲内」として扱う閾値(**5°**、PRD G6の±5°に対応)を導入した。導入後、逸脱0.4°のクリップは処方なし、逸脱8〜15°のクリップは処方あり、という妥当な分かれ方になることを確認した。

### 4.10 骨格推定の破綻を検出・補間する

品質ゲート(計測窓内の信頼できるフレーム比率)を導入したところ、**手元のデータの半分(8/16本)が不通過**だった。

#### 棄却した仮説(v1.4で追加)

原因の切り分けを行い、以下をいずれも実測で棄却した。**記録として残す。**

| 仮説 | 棄却の根拠 |
|---|---|
| 光量(ナイター)が原因 | ナイター4本中3本がスパイク4以上、昼間は0〜1と傾向はあったが、**昼間・スパイク着用の3本も4〜9箇所**で悪化した。光量単独では説明できない |
| 動作の速さが原因 | **これは症状を原因と誤認していた。**破綻クリップの大腿角速度2518°/sを根拠に「速すぎる」と結論したが、**健全フレームのみで測り直すと659°/s**で、通過クリップ(1142°/s)より遅かった。破綻したデータから計算した速度を原因として扱う循環論法だった |
| カメラ角度(真横だと脚が重なる) | 体の向きから逆算したカメラ相対角度と破綻率の相関は **r = +0.25**。説明力なし |
| 撮影距離(引き目が良い) | 画面内の体の縦幅と破綻率の相関は **r = +0.23**。説明力なし |
| 脚の重なり時間 | 2D上の左右くるぶし距離が近い時間の割合と破綻率の相関は **r = −0.26**。説明力なし |

n=16では変数(光量・履物・動作の種類・カメラ角度・距離・被験者・体の回転量)を分離できず、**根本原因は未特定のまま**である。

#### 不変量による検出と補間

原因を特定できないまま、次の一手として「**同一人物の骨の長さはクリップ内で変わらない**」という不変量を使う対策を実装した。

クリップ全体の骨長(股-膝、膝-足首、左右)の中央値から15%を超えて外れるフレームは、関節の対応付けを誤っている(左右の脚の取り違えなど)と判断できる。**なぜ取り違えたかを特定しなくても、「このフレームは信用できない」と機械的に言える。**破綻フレームは前後の健全フレームから座標を補間する(visibilityは書き換えず、そのフレームが不確かだった事実は残す)。

**効果: 品質ゲート通過率が 50%(8/16) → 75%(12/16) に改善。**通過していたクリップの値は変化しない(93°→93°、110°→110°)ため、壊れていないものを壊さないという条件も満たしている。

| クリップ | 窓内健全率 | 補間前 | 補間後 |
|---|---|---|---|
| 大人 07-31 | 15% | 117° / スパイク7 | 117° / **1** |
| 大人 07-33 | 31% | 122° / 4 | 122° / **1** |
| 大人 11-46 | 50% | 103° / 4 | 96° / **0** |
| 大人 11-47 | 23% | 120° / 6 | 112° / **1** |
| 大人 07-34 | 37% | 112° / 9 | 110° / 3(不可) |
| 11歳 07-27 | **0%** | 137° / 7 | 91° / 2(不可) |

窓内健全率が0%のクリップ(補間の元データが窓内に一枚もない)は原理的に復元できず、撮り直しを案内する。**この案内文も原因を断定しない書き方にした。**「真横から撮ってください」のような断定ではなく、試せる選択肢(離れて全身を映す/カメラ位置を変える/力を抑える 等)を並べる形とした。

**適用範囲の限定:** この方法が効いたのは、破綻が「関節の対応付けの誤り」という形で現れ、骨長という不変量に違反したためである。**あらゆる破綻に不変量が使えるという一般化はできない。**別の形の破綻(全体が一様にずれる等)には無効である。

**段階的な品質判定:** 窓内健全率10%未満は診断そのものを行わない。10〜25%は計測値を出すが処方は控える(`canPrescribe = false`)。25%以上で通常の診断を行う。実測で11%のクリップでも補間後に妥当な値が得られたため、完全に止めるのは情報がほぼ無い場合に限った。

**品質判定の基準そのものも一度誤っていた。** 当初「10°超の1フレーム変化」を不良としていたが、角速度2000°/s級の実戦キックでは120fpsでも1フレーム16°の変化が**正常に発生する**。符号が連続していれば本物の運動、反転していれば推定エラーとして切り分ける方式に改めた。

### 4.11 運動連鎖(近位→遠位)は参考指標として有効

キックを股関節→膝→足首の運動連鎖として捉え、大腿・下腿の角速度ピークの時間差(近位→遠位の順で加速するのが理想)を計測した。処方には使わないが、動作の質を反映する参考指標として有効と判断した。

- **屋外の実戦動作では連鎖の時間差が安定**(26/34/36ms、SD 5.3)
- **室内の軽い蹴りでは崩れる**(34/51/76/136ms、SD 44.6) — 運動連鎖が形成されていないことを示唆
- タイミング効率(ボール接触時/ピーク時の角速度比)は技量を分離しない(大人94〜97% 対 13歳69〜94%で重なる)が、**推定破綻の検出には有効**(異常クリップで20%、他は69〜97%)

**測れるのは運動連鎖4要素のうち2リンク分。** 足首は精度不足、軸足の踏み込み(水平方向の加速)は worldLandmarks が腰中点原点のため**原理的に取れない**。

**技量差は分離できなかった。** 同日・同場所・同履物で撮影した大人と13歳の対照ペアで、膝屈曲・角速度・連鎖差・効率のいずれも範囲が重なった。映像で観察された「振り下ろしの最中に曲げていて、インパクトまでに伸ばし切れていない」という課題を直接測る指標は未定義である(§16)。

### 4.12 診断画面への導線漏れと、保存ライブラリの追加

実装は完了していたが、**アプリのどこからも `DiagnosisView` を呼び出しておらず、実機で診断画面に到達できない状態が長く残っていた**(コードレビューで発覚)。撮影後の確認画面と、動画取り込み結果の画面の両方に、蹴り足選択+「診断を見る」導線を追加して解消した。

**教訓:** 「実装済み」と「到達可能」は別である。機能の完了判定に導線の確認を含める。

あわせて、`.fsc` が一時ディレクトリ(iOSがいつ削除しても仕様通りの領域)にしか残らず見返せない問題を解消するため、**撮影記録の保存ライブラリ**を追加した。直近20本を自動保存、お気に入りは最大5件(一言メモ付き、直近の枠から独立)。**出自(自分で撮った/受け取った)を明示的に記録する**のは、将来「前回比+5°」のような比較機能を作ったときに、他人の骨格が比較対象に混ざらないようにするため。

また、シートを開いている間もカメラと推論が動き続け、**姿勢トリガーが働いて見えないところで収録が始まる**バグを修正した。停止を `isSuspended` という明示的な状態として持たせ、画面追加時に漏れない構造にした。

## 5. UGC設計:審査型ライブラリ(開放型SNSにしない)

低品質・誤ったフォームの拡散を防ぐため、フィード型SNSではなく**キュレーションされた集合知**(Wikipedia型)として設計する。

**投稿フロー:** ①5秒動画を投稿(端末内で骨格化済み)→ ②AI自動審査(骨格信頼度/撮影条件/基準値適合)→ ③合格分のみ骨格アニメとして「みんなのお手本」へ、レベル帯に自動分類 → ④認定コーチ(バッジ制度)が任意でレビュー・解説付与。

**運用ルール:** 公開は骨格アニメ+匿名ハンドルのみ(生動画は本人・保護者限定)/リアクションは肯定系のみ(👏🔥「まねした」)、自由コメントなし/DM機能を作らない/週次チャレンジでテーマを限定/通報導線と24h対応SLA、未成年関連は最優先キュー。

**容量設計:** 解析用の高フレームレート・3D骨格(5秒で約240KB)をそのまま公開すると容量が想定の6倍になる。**公開用は30fps・2Dにダウンサンプリングした軽量版(約15KB)を別途生成する**(§10.2)。閲覧に高フレームレートと3Dは不要。

## 10. インフラ・コスト戦略

### 10.1 設計原則

1. **端末内完結の最大化** — 骨格推定・破綻補間・フェーズ検出・角度計算・基準値突合・ギャップ判定・処方生成まで、**解析パイプライン全体を端末内で実行する**。サーバーが必要なのは「コンテンツ配信」「処方の言語化(LLM)」「UGC共有」の3つだけ。**Phase 0で実機動作を確認済み。**
2. **自前サーバーを建てない** — バックエンドはBaaSを採用。
3. **骨格データの軽さを武器にする** — ただし想定サイズは実測で改訂した(§10.2)。

### 10.2 骨格データサイズ(実測)

| 用途 | 内容 | 5秒あたり(圧縮後) |
|---|---|---|
| v1.1想定 | 2Dのみ・30fps | 40KB |
| 解析用(実測) | 3D込み・30fps | 約75KB |
| 解析用(実測) | 3D込み・120fps級 | **約240KB** |
| 公開用(v1.5) | 2D・30fpsへダウンサンプル | 約15KB |

**UGCライブラリには公開用の軽量版のみを保存する。**1万投稿で約150MBとなり、BaaS無料枠に収まる。高精度な解析用データは端末内に留める。

**将来の削減余地:** 顔の10点(目・耳・口)はキック動作の分析に使用していない。除外すると約3割削減できる(実測 236.9KB → 162.4KB)。ただし**鼻は画角判定と向きの自己診断で体の上端として使うため残す必要がある。**手の指6点は複数競技展開時に必要になる可能性があるため保持を推奨。UGC容量が問題になる v1.5 で判断する。

## 11. システム構成

```
[モバイルアプリ(端末内で完結する処理)]
  ├─ 【撮影中】720p/30fps・軽量モデルでライブガイド
  │    └─ 全身の画角判定 → 静止検出 → 自動収録開始

  ├─ 【事後解析】全フレームを高精度モデルで処理(runningMode=video)
  │    └─ 33点+3D座標 → 骨長一貫性による破綻補間 → 局面検出 → 3Dで角度算出
  ├─ 基準値DB(同梱・差分更新)と突合 → 診断/処方 → 保存ライブラリ
  ├─ .fsc 書き出し・読み込み(F11)/ 公開用の軽量版生成(v1.5)
  └─ 処方キャッシュ(同一ギャップパターンはLLMを呼ばず再利用)
        │ 必要時のみ・軽量データのみ
        ▼
[BaaS(Supabase/Firebase — 自前サーバーなし)]
  ├─ 認証(匿名→保護者アカウント昇格)
  ├─ 公開用骨格データDB+審査キュー(v1.5)
  ├─ 参照コーチングDB・基準値の配信(出典・監修者・版管理)
  └─ お手本動画のCDN配信
        │
        ▼
[LLM API]  ※Phase 0では未使用
  └─ 処方文の言語化:計測値/基準値ギャップの構造化JSON → 三段構成の文章
     (セーフティフィルタ:医療助言・過負荷・ネガティブ表現の検出)
```

**ライブガイドと解析の分離が構造上の要点。**リアルタイム推論では時間解像度が足りず、逆に解析パスはリアルタイム制約がないため高精度モデルで全フレームを処理できる。

**LLMには動画を渡さず構造化データのみ。**生動画・生骨格の既定保存先は端末。

## 12. データとプライバシー

- 生動画:既定で端末内。UGC投稿時も**生動画は非公開**、公開は骨格データのみ
- 13歳未満:保護者同意必須。投稿機能は保護者の明示的な有効化が必要。広告なし・第三者提供なし・即時削除
- 骨格データの共有は匿名ハンドル。位置情報等のメタデータは投稿時に自動除去
- BaaS選定時にデータ所在地(リージョン)と暗号化を確認。分析利用は匿名化・オプトインのみ
- **MediaPipeが内部に持つ利用統計送信機構の挙動を、App Store申請前にネットワークログで確認する**(13歳未満を含むため)

## 14. リスクと対策

| リスク | 影響 | 対策 | 状態 |
|---|---|---|---|
| 基準値の妥当性不足 | 誤った指導 | 文献出典+複数コーチ監修+年齢帯別レンジ。「目安」として提示。体幹前傾は一次出典を確認できず撤回済み(§4.8) | 一部対策 |
| 計測値の撮影角度依存 | 基準値と比較不能 | 3D座標での角度計算+F1での角度指定+真横撮影の自動判定(§4.4) | 対策済み(閾値の妥当性は要検証) |
| 角度の規約の取り違え | 基準値と約20°ずれた比較 | `Convention`型で規約を明示し不一致を機械的に検出。角度定義v3へ更新(§4.2.1) | 対策済み |
| 時間解像度の不足 | インパクト時の指標が欠落 | 120fps級の録画と事後解析+測定窓の中央値方式(§4.7) | 対策済み |
| 骨格推定の断続的な破綻 | 品質ゲート不通過(実測50%) | 骨長一貫性による破綻検出・補間(§4.10)。**根本原因は未特定** | 対策済み(通過率75%) |
| 足首の伸びが処方に使えない | 指導上重要な指標が測れない | 参考値+一般的な指導ポイントに切り替え、判定はしない(§4.8) | 対策済み(処方は断念) |
| 上級者の全力シュートが計測不能 | 対象範囲の制限 | 非ゴールに明記。撮り直し案内で誤診断を防ぐ | 対策済み(範囲限定) |
| 高フレームレート時の露出不足 | 暗所で検出率低下 | 120fpsを上限とする。F1で明るさをガイド | **要検証**(ナイター実測でゲート通過0/2) |
| 端末の発熱 | 動作低下・離脱 | 720p/30fpsのライブガイド。録画は短時間 | 一部対策(**屋外炎天下は未検証**) |
| LLM費用の想定超過 | 原価崩壊 | 端末内処理の最大化、処方キャッシュ、βでの実費計測 | 設計済み |
| BaaS無料枠の仕様変更 | 費用増 | 骨格データの軽さにより移設容易。標準SQL/JSONでロックイン回避 | 設計済み |
| 言葉の参照が子どもに響かない | 価値実感の低下 | 自前お手本(視覚)との二層で補完。小学生モードの語彙を専門家監修 | 未検証 |
| 選手名の扱い | パブリシティ権 | 解説文脈のみで使用、機能名・広告では不使用。法務レビュー | 未着手 |
| UGCの低品質・誤フォーム拡散 | 上達阻害 | 審査型ライブラリ、週次チャレンジ、認定コーチレビュー | 設計済み |
| 未成年の露出・接触 | 重大な安全問題 | 骨格アニメのみ公開、匿名、自由コメント・DMなし、通報SLA | 設計済み |

## 16. オープンな論点

**実測で解決した論点**

- ~~骨格エンジンの選定~~ → MediaPipe 33点で確定(足部キーポイントが必須のため)
- ~~角度計算の方式~~ → 3D座標必須で確定(2Dは撮影角度依存で再現しない)
- ~~角度の規約~~ → 屈曲角/内角/鉛直からのずれを型で区別し、PRD・文献・実測を整合(§4.2.1)
- ~~実用フレームレートの決定~~ → 120fps級。測定窓の中央値方式と組み合わせて5〜8°/frame相当を達成
- ~~足首の伸びは処方に使えるか~~ → 構造的に不可能と確定(§4.8)。参考値+一般的な指導ポイントに切り替え
- ~~体幹前傾の基準値15〜20°は妥当か~~ → 一次出典を確認できず撤回(§4.8)
- ~~利き足の自動判定は可能か~~ → 不採用。足部キーポイントの不安定さで判定が反転する(§4.1.1)
- ~~骨格推定の断続的な破綻は放置するしかないか~~ → 骨長一貫性による補間で通過率50%→75%(§4.10)。**ただし根本原因は未特定**

**未解決の論点**

1. **基準値DBの監修体制と年齢・体格帯別レンジの粒度** (Alphaの最優先課題。膝屈曲1指標にまず絞る)
2. **文献の原典確認** — 膝屈曲の参照帯を支える Cordeiro 2015 / Greig 2018 はいずれも二次引用で原典未取得。発表・監修の場で提示する前に確認が必要
3. **対象動作の定義** — 強いシュートとロングパスで膝屈曲が20〜30°違う(実測)。同一の基準値で両方を判定すると誤診断になる。動作種別ごとの基準値、または撮影時の動作選択が必要
4. **「膝が伸び切らない」現象の指標化** — 映像で観察された課題(振り下ろし中に曲げ、インパクトまでに伸ばし切れない)を直接測る指標が未定義。軸足の踏み込みを基準にした時間軸が必要だが、腰中点原点の座標系では取れない
5. BaaSの最終選定(Supabase vs Firebase — Alphaのスパイクで決定)
6. フリーミアムの線引き(無料:解析+基本処方/有料:詳細処方・履歴無制限・チャレンジ特典)
7. 認定コーチバッジの審査基準と有料メンター化の是非
8. 骨格アバターの表現(棒人間かキャラクター性のあるアバターか)
9. UGC投稿規約(骨格データの利用許諾、退会時の扱い)
10. 撮影角度の担保方法 — 足長/下腿長比による自動判定は実装済み。**閾値0.22の妥当性**を、より多様な体格・年齢のデータで検証する必要が残る
11. 骨格推定が破綻する根本原因 — カメラ角度・光量・履物・動作速度のいずれとも相関しなかった(§4.10)。補間による実用対策は打てたが、原因不明のままである点はBetaでも継続調査
12. 運動連鎖(§4.11)の基準値 — 参考指標として有効性は確認できたが、処方に使える段階の基準値はまだない
